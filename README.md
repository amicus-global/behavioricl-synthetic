# BehaviorICL — synthetic demonstration copy

Leave-one-app-out In-Context Learning pipeline for predicting individual
behavioural traits from a participant's history across economic games. A
participant's behaviour in every game *except* one is written out as a
natural-language prompt; a language model predicts the held-out game's outcome.

This copy runs on **synthetic data**. The participant records in
`0_Preprocess/synthetic_data.csv` are generated by
`0_Preprocess/make_synthetic_data.py`, not collected from anyone, and they
contain no study data. Anything the pipeline produces here — prompts, model
outputs, metrics — demonstrates the code; none of it is a research result.

## Setup

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

## Run it

Offline, with no API key and no spend. `BEHAVIORICL_MOCK=1` swaps the model call
for a deterministic arithmetic stand-in (`2_Inference/mock_backend.py`), which
is enough to exercise every stage:

```bash
export BEHAVIORICL_MOCK=1
./run_demo.sh cooperation      # one trait, ~30 seconds
./run_demo.sh                  # all nine traits + cross-trait reports, ~7 min
```

Against the real API:

```bash
unset BEHAVIORICL_MOCK
export OPENAI_API_KEY=...       # your own key; none ships with this copy
python 2_Inference/run_trait.py cooperation
```

The model defaults to `gpt-4o`; set `BEHAVIORICL_MODEL` to change it
(`gpt-4o-mini` for cheap tests), and optionally `BEHAVIORICL_TEMPERATURE` and
`BEHAVIORICL_SEED`. Every output row records the model, temperature and seed
it was made with (null means the provider default). One trait over the 240 synthetic participants is about 700
calls across the three inference variants. `run_trait.py` appends to its output
files and skips participant codes it has already written, so an interrupted run
can just be restarted. No inference outputs ship with the repo, so a first run
starts from scratch.

Numbers from mock mode are a property of the stand-in and of the data generator,
so don't read anything into them; the `_THESE_ARE_NOT_RESULTS.txt` notes in
`2_Inference/` and `3_Eval/` repeat that next to the output files. One cosmetic
quirk: zero-shot Pearson r comes out as `nan` for `coordination`, because a
zero-shot prompt carries no history, the stand-in therefore returns a
near-constant value, and rounding onto that trait's quarter grid flattens it to
an exact constant. A real model does not behave that way.

## How the design works

Each of the nine traits names one target app. For a given trait, every game
*except* that app is rendered as a block of plain English, the target app's
block is omitted, and the trait's prediction question is appended. Three traits
(`risk_tolerance`, `altruism`, `morality`) are sub-tasks inside the single
`games_solo` app, so they hold out only their own sub-task via
`games_solo_exclude` and keep the rest of the app as context.

Each prompt is then sent three ways:

| Variant | Context given to the model |
|---|---|
| ICL | the participant's own behavioural history |
| Zero-shot | no history, just the game description and the question |
| Other-student ICL | a randomly chosen other participant's history |

The third is the control that separates "the model read *this* person's history"
from "the model knows the base rate".

Traits: `trust`, `competitiveness`, `cooperation`, `coordination`,
`depth_of_reasoning`, `tolerance_for_inequality`, `risk_tolerance`, `altruism`,
`morality`.

`trust` is the one special case. It needs the partner's send, looked up
dyadically, to state the receiver's budget, and it returns two numbers rather
than one, so it goes through `call_model_trust()` instead of `call_model()`.

`1_Prompts/trait_configs.py` is the single source of truth for all of this: per
trait, which app to hold out, which columns are the target, the legal output
range, the game description shown to the model, and the prediction question.
Adding a trait means adding one entry there.

## Layout

```
0_Preprocess/
  make_synthetic_data.py   generates synthetic_data.csv
  check_synthetic_data.py  asserts every value is in range and on grid
  validity_matrix.py       per-app validity filter
  synthetic_data.csv       240 synthetic participants, 111 columns
  validity_matrix.csv      which participants are usable in which app
1_Prompts/
  trait_configs.py         the 9 trait definitions
  build_prompts.py         behavioural history -> prompt, target app held out
  <trait>/prompts.jsonl
2_Inference/
  client.py                model wrapper (BEHAVIORICL_MODEL etc.)
  mock_backend.py          offline stand-in for running without a key
  run_trait.py             runs the three variants, with checkpointing
  <trait>/{icl,zero_shot,other_student_icl}_results.jsonl
3_Eval/
  eval_trait.py            MAE, Pearson r, bootstrap CIs, Wilcoxon, SD calibration
  pca_baseline.py          leave-one-trait-out PC1 benchmark
  ml_benchmarks.py         OLS / Lasso / Random Forest benchmark
  cross_trait/             cross-trait report and baseline outputs
```

`run_demo.sh` chains the stages; to drive them by hand, run them in order, since
each reads the previous one's output:

```bash
python 0_Preprocess/make_synthetic_data.py
cd 0_Preprocess  && python validity_matrix.py
cd ../1_Prompts  && python build_prompts.py <trait>
cd ../2_Inference && python run_trait.py <trait>
cd ../3_Eval     && python eval_trait.py <trait>
```

## The synthetic data

240 participants in 10 sessions of 24, with 111 columns named exactly as the
original oTree export names them, so the pipeline consumes the file unchanged.

Each synthetic participant draws five independent latent factors — prosociality,
risk appetite, reasoning depth, patience, slider ability — and every decision is
a noisy monotone transform of those, clipped and rounded onto the game's legal
grid. Because prosociality loads on several games, the file contains a
cooperative-phenotype structure for the ICL prompts and the PCA baseline to pick
up. The generator's parameters come from the legal range of each decision
variable plus generic plausibility; they are not estimates of anything.

The generator also injects realistic mess on purpose, so the validity filter has
work to do: some dyads are left half-empty, which invalidates both members, and
some participants are missing a whole app. In the shipped file 218 of 240
participants are valid in `trust`, and per-trait samples run from 209
(coordination) to 239 (the `games_solo` traits).

Regenerate, or make a bigger file:

```bash
python 0_Preprocess/make_synthetic_data.py                 # 240, seed 20261019
python 0_Preprocess/make_synthetic_data.py --n 960 --seed 7
```

The seed is fixed, so the shipped `synthetic_data.csv` reproduces byte for byte.
After changing the generator, check it:

```bash
python 0_Preprocess/check_synthetic_data.py
# 8,638 value checks / 212 trust-dyad consistency checks / 240 unique codes -> PASS
```

### Valid ranges

The grid every decision variable has to land on, from the oTree game
definitions. `check_synthetic_data.py` enforces these.

| Game | Decision | Range |
|---|---|---|
| Competition (slider task) | pay scheme | 0 = fixed 0.20/slider, 1 = 0.50/slider if ahead of partner |
| | sliders centred | 0–48 |
| Mutual aid, 4 rounds | credits sent | 0.0–1.0, step 0.1, doubled on arrival |
| Coordination, 4 rounds | option | "A" (pays 3) or "B" (pays 5 if matched, else 0) |
| Guessing game, 4 rounds, groups of 4 | guess | 0–100; target is {1/3, 1/2, 2/3} × group mean |
| Individual battery | time allocation | 0–5 credits moved to next month, doubled |
| | BRET boxes opened | 0–10, one of the ten hides a bomb |
| | dictator gift | 0–10 of a 10-credit endowment |
| | moral decisions | 5 binary choices, self = 2/4/6/8/10 vs 10 to UNICEF |
| | die report | 1–6 |
| Redistribution | split of 10 credits | integer 1–9, stored as Participant B's share |
| Trust | send | 0–5, step 0.5, tripled on arrival |
| | return | 0 to 3 × partner's send |

One caveat if you build on the redistribution variables: the `redistribute` app
stores Participant B's credits, while the prompt builder reads
`redistribute_team`'s decision as Participant A's. The synthetic data follows
each builder's own assumption, so the demo is self-consistent, but confirm the
direction before using the team variable on real data.
